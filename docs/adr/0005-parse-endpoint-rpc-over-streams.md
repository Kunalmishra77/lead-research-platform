# ADR-0005: The parse endpoint calls the workers over Redis Streams

- Status: Accepted
- Date: 2026-09-23

## Context

`POST /app/research/parse` turns a sentence into a ResearchSpec the user can review before any
credits are spent. It is the only synchronous, user-facing call in the product that needs a model,
and docs/05 leaves the mechanism to this ADR.

Everything the call needs already exists in Python: the prompt registry, the schemas, the response
cache, the per-job cost cap, the `usage_events` metering, `spec_draft.build_spec`, and an eval set
that says how well it works. None of it exists in TypeScript.

## Options considered

1. **An API-side LLM call through a TypeScript gateway client.** One hop, no queue involved. But
   it means a second AI gateway: prompts and schemas duplicated or loaded across the language
   boundary, a second response cache, a second metering path, and a second implementation of the
   repair retry. Two implementations of "what spec_parse does" drift, and the eval set only ever
   measures one of them. It also breaks docs/07's rule that no module outside the gateway calls a
   provider.
2. **RPC over Redis Streams.** The API publishes a `research.parse` envelope and waits for a reply
   on a key it generated; a worker does the work through the existing gateway. One implementation,
   already evaluated, already metered. The cost is a queue hop on a user-facing path, and a new
   failure mode: no worker listening.
3. **Make the endpoint asynchronous** (return a job id, stream the result over SSE). Uniform with
   the rest of the job system, but the New Research page (docs/09) needs the parse in front of the
   user before they can edit it, and a spinner plus an SSE subscription for a two-second call is a
   worse experience than a request that waits.

## Decision

Option 2. The API publishes to the `interactive` pool and blocks on a reply key with a 20-second
timeout.

- The reply key is `rpc:reply:{job_id}`, **generated by the API**, never taken from the request.
  A client-supplied key would let anyone choose where a worker writes in Redis.
- The worker replies with `LPUSH` + `EXPIRE`; the API waits with `BLPOP`. A list gives exactly the
  timeout semantics needed and disappears on its own if nobody is waiting.
- The reply is a contract (`packages/contracts/schemas/research-parse-reply.schema.json`),
  validated on both sides, because it crosses the language boundary like every other envelope.
- A failure replies too, with a classified error, so the caller fails in a second rather than
  waiting out the timeout.
- `interactive` is its own pool so a backlog of discovery work cannot delay a user waiting for a
  parse.

The credit estimate is **not** computed in the worker. The rate card is per org and lives in the
database behind RLS; the worker returns the spec and the API prices it with the same
`CreditsService.estimate` that the create endpoint reserves against, so the number the user sees
is produced by the code that will charge them.

## Consequences

- One implementation of `spec_parse`, measured by one eval set, metered through one gateway.
- A new user-visible failure: nothing consuming `jobs:interactive` means a 503. The endpoint
  checks for a registered consumer before it publishes, so a deployment that forgot
  `WORKER_POOLS=...,interactive` fails in milliseconds and says why. Redis keeps a consumer
  registered after its worker dies, so a crashed pool still waits out the timeout — the check
  catches the misconfiguration, not every absence.
- A failed parse is **not** retried. The caller has already been given its classified error and
  has stopped listening, so a retry would be a paid model call whose answer goes nowhere. A user
  who wants another attempt asks for one. (A malformed payload or a reply key that is not this
  job's are API bugs rather than user input; both surface as the 503, since there is nowhere
  trustworthy to reply to.)
- A parse is capped like job work. The spend counter keys on the research job where there is
  one and on the envelope's own id where there is not, so `PARSE_COST_CAP_MICROS` is a real
  ceiling and a retried envelope shares one allowance instead of getting a fresh one.
- Error text from a worker reaches an end user through this path, so it goes through the same
  redaction as every other escaping error (docs/10).
- The parse is cached by the gateway (24 h, per org), so a user retrying the same sentence pays
  once, and the second call returns in milliseconds.
- Parsing costs model tokens but reserves no credits, so the endpoint needs its own rate limit;
  without one it is an unmetered way to spend our money.
- If a second interactive AI call ever appears, this pattern generalises: the envelope type and
  the reply schema change, the transport does not.
