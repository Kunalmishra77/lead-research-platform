# Phase 3 — Crawling & Extraction

## Goal
For every candidate with a website, crawl the key pages legally and extract description, contacts, socials, tech and team info into provenance-tracked, normalized field values.

## Read before starting
docs/06 sections 4-6, 07 (field_extract, page_classify, grounding), 08 (policy), 10 (SSRF), 13 (golden datasets)

## Tasks
- [x] 3.1 Crawl frontier (Redis), per-domain politeness, global concurrency per pool — `app/crawl/frontier.py`; the claim is one Lua script, which is what makes per-host concurrency 1 true across workers rather than only within one
- [x] 3.2 robots.txt fetch/cache/evaluate with protego; crawl-delay support
- [x] 3.3 HTTP fetcher: httpx HTTP/2, timeouts, body cap, conditional GET, redirects cap, SSRF guard, honest UA — `app/crawl/fetcher.py` over `ConnectorHttpClient` (ADR-0013), with redirects followed by hand so robots and the SSRF guard run on every hop

- [ ] 3.5 Browser fetcher (Playwright pool) used only on SPA-shell heuristic; resource blocking; timeouts
- [x] 3.6 Raw store with content-hash dedupe; raw_documents rows (partitioned) — migration 0028 (`raw_documents` partitioned monthly by `fetched_at`, plus the non-partitioned `raw_document_keys` that carries `unique(url_hash, content_hash)` and is the only thing `field_values.raw_document_id` can point at, ADR-0003); `app/crawl/rawstore.py` (the key docs/06 §4.9 defines, gzip, write-and-rename, 90-day prune) and `app/db/raw_documents.py` (one row per fetch, dedupe in one indexed lookup). **Not S3 (ADR-0019):** measured at 30 KB gzipped per page, 0.58 pages per crawl and 38% of leads crawlable, a lakh of leads is ~660 MB against the 1 GB free plan, while the worker host has 134 GB. A refusal is recorded too — "this door was shut on this date" is the answer to "why has this company no email". Every crawled value now names the *copy* it was read from, which is what `source_url` stops answering the moment the page changes.
- [x] 3.7 Page discovery: homepage links + sitemap -> choose contact/about/team/careers/services pages (rules) — `app/crawl/discovery.py`; anchor text beats an opaque URL, the sitemap is only read for roles the homepage left unfilled
- [x] 3.8 Extractors: JSON-LD/microdata/OpenGraph (extruct), contacts (emails incl. de-obfuscation, phones, WhatsApp), social links, address from footer — `app/crawl/structured.py` (nodes ranked, so a breadcrumb trail is not the company name) and `app/crawl/contacts.py` (a `mailto:`/`tel:` href outranks text; a phone must be valid per `phonenumbers`, not merely possible)
- [ ] 3.9 Tech detector with open fingerprint set + DNS MX/TXT — **DNS half done**, fingerprint half not, and deliberately left unticked rather than claimed. `app/crawl/dns_records.py` reads a domain's MX records once per crawl and writes two values: `mail_exchanger` (found — the host a sender hands mail to) and `mail_provider` (`derived_pattern` — the hostname is the evidence, the label is our reading). The patterns come from the graph, not a vendor list: measured over 495 domains, seven suffixes cover two thirds of those that have mail at all (Google 69, Hostinger 50, Microsoft 365 22, GoDaddy 12, Zoho 8), and the rest run their own `mail.<domain>`. **51% have no MX at all** — collected as an absence, because "therefore undeliverable" is task 4.5's verdict and not this one's. The resolver is injected so no test touches live DNS. **What is left:** HTML/header/cookie fingerprints. The widely-used dataset stopped being openly licensed in 2023, so this needs a permissive source or none — the same question ADR-0018 answered for transliteration, and it should not be settled by quietly vendoring something.
- [ ] 3.10 Page classifier (rules + small model fallback)
- [ ] 3.11 LLM field extraction for description/services/products/team members with evidence validation
- [x] 3.12 Normalizers: phone, email, URL/domain (+platform domains list), name, social handles, address basic, industry mapping — `app/normalize/`: `phones.py` (phonenumbers against the company's country; 481 national-format numbers were being dropped for want of a `+`, 57% → 99% of companies with a phone are now dialable), `emails.py` (one spelling per mailbox, plus the `email_role` flag the crawl had always computed and thrown away), `names.py` (ADR-0018: `anyascii` rather than GPL `unidecode`; 11 matching keys held characters no plain spelling could match, two of them written in mathematical bold capitals), `cities.py` + the lookup in `handlers/discovery.py` (one city was stored under three spellings and another under four — a customer filtering "Gurgaon" saw 9 of 970). `domains.py` and `social_from_url` were already shared and were left where they are. **Not done, and not pretending otherwise:** parsing a free-text address into components, which matters only for footer addresses the crawler reads — the place index already publishes street, house number, postcode and lat/lng separately. Industry mapping is the taxonomy from 2.1/ADR-0017.
- [x] 3.13 Best-value computation for companies after each batch — `app/db/best.py`, called by `_store_chunk` inside the same transaction as the values it derives from. `distinct on (entity_id, field) ... order by confidence desc, observed_at desc` is the whole computation (docs/04). `companies.best` had existed since migration 0012 and held `{}` for all 1,550 companies; it is now populated for every one. A derived cache and never a source: deleting the column and recomputing it would lose nothing. Deliberately projects only `companies.state` into a column — `_company_params` had been writing a literal `None` there for every company ever stored, so 1,546 of 1,550 had no state and no state filter could work. It goes through `ReferenceData.find_state` (new; `find_area` prefers a city on a tie and "Delhi" is both), so `HR` 870 and `Haryana` 245 are one state; `Gurugram`, `India`, `IN` and `CA` all arrived in that field too and are stored as nothing rather than as a state. **Not projected:** any field that already has a column written from the candidate — the city *value* says "New Delhi" because the source did and the city *column* says "Delhi" because that is what filters read, and two writers for one column means the later one silently wins.
- [ ] 3.14 Golden dataset (50 saved sites) + quality report command — **harness done, corpus at 2 of 50 reviewed** (10 harvested), and left unticked for that reason. `app/golden/`: a harvester that draws from the live graph, a scrubber, an inspector for labelling, and `python -m app.golden report`. **ADR-0020:** the repository is public and 14 of 22 surveyed homepages carried a named individual's address, so a page is kept as real structure with synthetic contact values — and the substitution *is* the label, which is what makes the expectations independent of the code under test. Three label categories (`expect`, `also_theirs`, `absent`), because the first two alone made a correct extraction count as a false positive on the first site reviewed. Gates: `test_golden_corpus_is_publishable.py` (every contact-shaped string in every fixture is one the scrubber wrote — it has already caught a value dropped from a label during review) and `test_golden_report.py` (no false positives ever, plus a recall floor). Corpus 1.7 MB, 100% recall over 4 labelled fields. **Growing it to 50 is the remaining work, and it is hand labelling rather than code.**
- [x] 3.15 Web: results grid shows website, emails, phones, socials, tech with provenance badges and popover; company drawer basic — Email and Profiles columns, and a `<details>` drawer per lead carrying every field with its source, date, confidence and a link to the page it was read from. The Technology group arrived with 3.9's DNS half (mail host and who runs it); it will grow when the HTML fingerprints do.
- [x] 3.16 Metrics: crawl success ratio, restricted count, stage durations, cost per candidate — migration 0029 `app.admin_crawl_health(audit_id, since, ip, user_agent)`, staff-gated and audited like the other admin functions, plus `GET /app/admin/crawl` and a Crawl panel on the admin connectors page. SQL over rows the pipeline already writes rather than a metrics backend: there is none and no budget for one (ADR-0002), `research_tasks`, `raw_documents` and `usage_events` already carry everything the task asks for, and a counter kept in a worker would be lost on every deploy — this deployment redeploys several times a day. Verified against the numbers Phase 3 had measured by hand: 607 tasks, 351 pages, 348 that never got a page, 2,066 values, avg 12.9s / p95 28.1s. The refusal count comes from `raw_documents.access_status`, which only exists because of 3.6. **Named for what it measures:** the crawl calls no paid API, so a "crawl cost" column would always read zero; the figure is the whole pipeline's spend over the leads it delivered, and it is null rather than zero when nothing was delivered, because 0 would read as free.

## Acceptance criteria
- Golden set: email precision >= 95%, phone precision >= 95%, social link precision >= 95%, description present >= 85%.
- Robots disallow and restricted pages are never fetched/retried (tests prove it).
- SSRF tests: private IPs, metadata IP, file:// all blocked.
- Browser used on < 15% of fetched pages on a 500-site sample.
- Cost per Standard-depth candidate measured and recorded in PROGRESS.md.
